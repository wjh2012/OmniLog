# OmniLog

JSON API로 제공하는 위키. FastAPI + SQLite, 외부 서비스 의존성 없음.

## 실행

```bash
uv sync --group dev
uv run uvicorn main:app --reload
```

대화형 문서는 <http://127.0.0.1:8000/docs> 에 뜹니다. DB 파일은 작업 디렉터리의
`omnilog.db`이고, `OMNILOG_DB` 환경변수로 바꿀 수 있습니다.

```bash
uv run pytest
```

슬러그·리비전·트라이그램처럼 이 문서에 나오는 용어는 [용어집](GLOSSARY.md)에
정리해두었습니다.

## MCP

REST 라우트는 `/mcp`에도 그대로 MCP 툴로 노출됩니다(`fastmcp`). 기본값(PoC 단계)은
`OMNILOG_API_KEYS`가 비어 있으면 REST·MCP 모두 인증 없이 열려 있습니다.

배포 전에는 `OMNILOG_API_KEYS`에 `{"토큰": ["역할", ...]}` 형태의 JSON을 넣어 잠급니다.
역할은 `viewer`(읽기) / `editor`(쓰기) / `admin`(`/api/maintenance/compact`)이고, 상위
역할을 쓰려면 하위 역할도 같이 나열해야 합니다.

```bash
export OMNILOG_API_KEYS='{"sk-viewer-...": ["viewer"], "sk-admin-...": ["viewer", "editor", "admin"]}'
```

이 키가 설정되면 REST 요청은 `Authorization: Bearer <토큰>` 헤더가 필요하고, MCP
쪽에서는 같은 토큰이 보유한 역할만큼만 툴 목록에 나타나고 호출할 수 있습니다
(`omnilog/auth.py`, `omnilog/mcp.py`).

## 저장 구조

본문은 파일이 아니라 DB에 들어갑니다. 그리고 본문을 리비전 행에 담지 않고,
MediaWiki처럼 메타데이터와 본문을 분리했습니다.

```
page ──latest_rev_id──▶ revision ──text_id──▶ text
                            │                (불변, 512B 이상 gzip)
                            └──parent_id──▶ revision

source ──text_id──▶ text     ← 인용문도 같은 본문 저장소를 씁니다
       └─file_id──▶ file     ← 파일 바이트, sha256으로 키잉
```

### 테이블별 역할

| 테이블 | 담는 것 | 수명 |
|---|---|---|
| `text` | 본문 바이트, 또는 블롭 안 위치를 가리키는 포인터 | 덧붙이기 전용. 재인코딩은 압축 작업만 |
| `blob` | 한 구간의 payload를 묶어 한 번 압축한 스트림 | 압축 작업이 생성 |
| `revision` | 한 판본의 메타데이터 + 본문 포인터 | 덧붙이기 전용 |
| `page` | 현재 슬러그·제목·최신 리비전 포인터 | 편집마다 갱신 |
| `pagelink` | 현재 리비전이 내보내는 링크 대상 | 편집마다 통째로 교체 |
| `citation` | 현재 리비전이 인용한 출처 | 편집마다 통째로 교체 |
| `source` | 문서와 따로 관리하는 출처 자체 | 문서와 무관하게 살아있음 |
| `file` | 파일 출처의 바이트, 해시로 키잉 | 가리키는 출처가 없어지면 삭제 |
| `redirect` | 옛 이름 → page id | rename·별칭 조작 시 |
| `render_cache` | **현재 리비전**의 렌더링 결과 (gzip) | 페이지당 한 행 |
| `page_fts` | 검색 인덱스 | 편집마다 교체 |

`revision`이 메타데이터만 갖는 게 핵심입니다. 500개짜리 이력을 나열해도 본문은 한
건도 읽지 않습니다. 편집하면 `text`에 새 행을 쓰고 새 리비전이 그걸 가리킬 뿐,
앞선 행이 가리키던 내용은 바뀌지 않습니다.

`text`는 **논리적으로** 불변입니다. 어떤 `text.id`가 돌려주는 문자열은 절대 바뀌지
않습니다. 물리적 인코딩은 불변이 아닙니다 — [압축 작업](#압축과-유지보수)이 행을
델타로 다시 인코딩하거나 payload를 블롭으로 옮길 수 있습니다. `git repack`이 하는
것과 같은 거래입니다.

`flags`가 그 행을 어떻게 읽어야 하는지 알려줍니다:

| `flags` | `data` | 읽는 법 |
|---|---|---|
| `utf-8` | 본문 | 그대로 |
| `utf-8,gzip` | 압축된 본문 | 압축 해제 |
| `utf-8,blob` | 비어 있음 | 블롭에서 `offset`~`length` 잘라내기 |
| `…,delta` | | 위 결과를 `base_id`에 적용 |

### 정체성과 주소는 다르다

| 컬럼 | 성격 | 바뀌는가 |
|---|---|---|
| `page.id` | **정체성** | 절대 안 바뀜 |
| `page.slug` | 주소 | 언제든 |
| `page.title` | 표시 이름 | 언제든 |

리비전·별칭·렌더 캐시는 전부 `page.id`로 매답니다. 그래서 슬러그를 바꿔도 아무것도
따라 고칠 게 없습니다. 별칭이 슬러그가 아니라 page id를 저장하는 이유도 이것이고,
그 덕에 리다이렉트 체인이 아예 생길 수 없습니다.

**딱 한 곳만 예외입니다.** `pagelink.to_slug`는 id가 아니라 이름을 담습니다. 링크는
아직 존재하지 않는 문서를 가리킬 수 있어서 매달 id가 없기 때문입니다. 빨간 링크가
가능한 이유이자, rename이 `pagelink`를 고쳐 쓰지 않는 이유이며, 역링크 조회가
문서의 **모든 이름**으로 찾아야 하는 이유이기도 합니다.

### rename이 실제로 건드리는 것

`위키 시스템` 문서를 만든 직후:

```
text      id=1  flags=utf-8  data='설계 문서.'
page      id=1  slug=위키-시스템  title=위키 시스템  latest_rev_id=1
revision  id=1  page_id=1  number=1  text_id=1  parent_id=NULL
```

`OmniLog 위키`로 rename한 뒤:

```
text      id=1  flags=utf-8  data='설계 문서.'        ← 그대로. 새 행 없음
page      id=1  slug=omnilog-위키  title=OmniLog 위키  latest_rev_id=2
                └── 세 컬럼만 UPDATE. id는 그대로
revision  id=1  page_id=1  number=1  text_id=1  parent_id=NULL
          id=2  page_id=1  number=2  text_id=1  parent_id=1   ← text_id 재사용
redirect  from_slug=위키-시스템  to_page_id=1                  ← 한 행 추가
```

본문 바이트는 **한 번도 복사되지 않습니다.** 이동 리비전이 직전 리비전의 `text_id`를
그대로 가리키기 때문입니다. 본문이 불변이라 두 리비전이 한 블롭을 공유해도 안전합니다.

문서를 파일로 저장했다면 rename은 파일을 실제로 옮기는 일이고, 경로를 기억하던 이력·
링크·캐시를 전부 따라 고쳐야 합니다. DB에는 애초에 **옮길 "위치"라는 게 없습니다.**
슬러그는 컬럼에 담긴 라벨일 뿐입니다.

### 렌더 캐시

본문이 불변이라 `render_cache`를 `rev_id` 하나로 키잉할 수 있습니다. 다만 걸리는 게
하나 있습니다. `[[위키링크]]`는 대상이 살아있는 문서인지, 옛 이름인지, 아예 없는지에
따라 다르게 렌더링되는데 **이건 본문과 무관하게 바뀝니다.** 그래서 캐시 행마다 링크
대상 목록과 "렌더 시점에 각 대상이 어떻게 해결됐는지"의 해시를 함께 저장합니다.
링크된 문서를 새로 만들거나 이름을 바꾸면 그걸 가리키던 모든 문서의 캐시가 정확히
무효화됩니다.

**문서당 현재 리비전 하나만 캐싱합니다.** 처음에는 조회된 모든 리비전을 캐싱했는데,
그러면 캐시가 "지금까지 한 번이라도 열람된 리비전 수"만큼 자랍니다. 상한이 없습니다.
과거 리비전을 한 번 열어보면 그 HTML이 영구히 남았습니다. 실측에서 이 테이블이 DB
파일의 57%를 차지했습니다. 지금은 페이지당 한 행이고 HTML도 gzip으로 저장합니다.
과거 리비전은 요청 시 렌더링하고 캐싱하지 않습니다 — 드문 접근이라 캐시할 값어치가
없습니다.

## 압축과 유지보수

쓰기 경로는 항상 싼 길을 택해 본문 전체를 저장합니다. 줄이는 일은 나중에 따로
합니다. `git commit`과 `git gc`가 분리돼 있는 것과 같습니다.

> Git도 diff를 저장하지 않습니다. 매 커밋마다 파일 전체를 blob으로 저장하고, 델타
> 압축은 `git gc`가 packfile을 만들 때만 일어납니다. MediaWiki의 리비전 재압축도
> 같은 구조입니다.

`POST /api/maintenance/compact`가 두 가지 일을 합니다. **서로 독립적인 축**이라 하나만
해도 효과가 있습니다.

### 1단계 — 델타: 리비전 사이의 중복을 없앤다

**키프레임 방식**입니다. 16개마다 하나는 본문 전체로 남기고, 나머지는 그 키프레임에
대한 델타로 저장합니다. 페이지의 **현재 본문은 언제나 전체로 유지**합니다.

```
위치  0    1    2   …   15   16   17   …   최신
     전체  Δ0   Δ0      Δ0   전체  Δ16      전체
```

델타는 키프레임만 가리키고 다른 델타는 절대 가리키지 않습니다. 그래서 **어떤 리비전을
읽어도 델타 적용은 최대 한 번**이고, 현재 문서를 읽을 때는 아예 없습니다. 체인을 따라
걷을 일도, 체인 깊이를 조정할 일도 없습니다.

Git이 `pack.depth` 기본값 50에서 체인을 끊는 것도 같은 이유입니다. Git도 사실
키프레임을 쓰며 간격이 50일 뿐이고, 우리는 읽기를 더 싸게 사려고 16으로 잡았습니다.

델타 형식은 줄 단위이고 압축 전에는 그냥 텍스트입니다 (`omnilog/delta.py`). 어차피
위에 gzip이 얹히므로, 몇 바이트 아끼는 것보다 읽을 수 있는 인코딩이 낫습니다.

### 2단계 — 묶기: 압축 단위를 키운다

gzip은 **자기가 보고 있는 범위 안에서만** 반복을 찾습니다. 그리고 호출이 끝나면 그
범위를 전부 잊습니다. `text` 행마다 따로 압축하면 행 수만큼 창을 비우는 셈이고, 짧은
델타에는 20바이트짜리 gzip 헤더가 내용물보다 비싸집니다.

그래서 한 구간의 payload를 이어붙여 **한 번만** 압축하고 `blob` 행 하나에 담습니다.

```
blob 행 1  →  gzip( 키프레임 본문 ‖ 델타1 ‖ 델타2 ‖ … ‖ 델타15 )

text 행 1  →  flags='utf-8,blob'        blob_id=1  offset=0      length=25014
text 행 2  →  flags='utf-8,blob,delta'  blob_id=1  offset=25014  length=402
text 행 3  →  flags='utf-8,blob,delta'  blob_id=1  offset=25416  length=388
```

묶인 행은 `data`가 비고 **블롭 안의 위치를 가리키는 포인터**가 됩니다. MediaWiki가
`text` 행을 `DB://cluster/id` 포인터로 바꾸고 실제 묶음을 외부 저장소에 두는 것과 같은
자리입니다.

키프레임과 그 델타들이 한 스트림에 들어가므로, 델타에 반복되는 문자열을 gzip이 서로
참조로 대체합니다. **현재 리비전은 묶지 않습니다** — 살아있는 문서를 읽을 때 블롭을
통째로 푸는 일이 없어야 하니까요.

델타와 그 베이스는 같은 블롭에 있습니다. 그래서 읽기 한 번 동안만 유효한 작은
캐시(`BlobCache`)를 둬서 같은 스트림을 두 번 풀지 않게 합니다.

> MediaWiki의 `ConcatenatedGzipHistoryBlob`은 **델타를 전혀 쓰지 않고** 본문을 통째로
> 담은 뒤 묶어서 압축하기만 합니다. 묶기가 델타와 무관하게 단독으로 효과가 있다는
> 증거입니다. 델타 체인을 쓰는 쪽은 `DiffHistoryBlob`이고, 블롭당 100개·10MB에서
> 끊습니다.

### 안전장치

압축은 멱등입니다. 델타나 블롭이 원본보다 크면 그 대상은 건드리지 않습니다. 재인코딩
직후 해당 행들이 전부 원래 문자열로 되돌아오는지 확인한 뒤에만 커밋합니다.

### 실측

리비전 61개, 본문 하나 약 25KB인 문서 기준.

**본문 저장량** (`text` + `blob`):

| 단계 | 크기 | |
|---|---:|---|

VACUUM 뒤에 체크포인트까지 수행한 다음 크기를 보고합니다.

## 이름 변경

`POST /api/pages/{slug}/rename`은 문서를 옮기면서 옛 슬러그를 별칭으로 남깁니다.
기존 URL과 기존 `[[위키링크]]`가 그대로 동작합니다. 별칭을 남기고 싶지 않으면
`leave_redirect: false`를 넘기면 됩니다. `title`만 넘기면 슬러그는 그대로 두고
제목만 바꿉니다. **주소가 바뀌는 건 항상 명시적으로 `slug`를 넘겨야 합니다.**

이동이라고 하지만 옮겨지는 건 없습니다. `page` 행의 컬럼 값이 바뀔 뿐이고 본문은
제자리에 그대로 있습니다. 어떤 행이 실제로 어떻게 바뀌는지는
[저장 구조](#rename이-실제로-건드리는-것)에 적어뒀습니다.

별칭은 슬러그가 아니라 **page id를 저장합니다**:

```
rename A → B → C

redirect: A ─┐
             ├──▶ page (현재 slug = "c")
redirect: B ─┘
```

그래서 모든 옛 이름이 페이지를 직접 가리킵니다. **리다이렉트 체인과 순환이
만들어질 수 없고**, 해결은 항상 정확히 한 홉입니다. 따라갈 체인도, 조정할 순환
카운터도 없습니다.

충돌 규칙:

- 살아있는 문서 위로, 또는 다른 문서의 옛 이름 위로 rename하면 `409`
- **자기 자신의** 옛 이름으로 rename하면 그 이름을 회수하고 이제 무의미해진 별칭을
  지웁니다. 이름을 왔다갔다 바꾸는 게 됩니다
- 남의 옛 이름 자리에 새 문서를 만들면 조용히 가로채는 대신 `409`. 가로채면
  rename이 남긴 링크 흔적이 끊기기 때문입니다
- `DELETE /api/pages/{slug}`는 **별칭을 따라가지 않습니다.** 옛 이름을 주면 그
  별칭만 지우고 문서는 그대로 둡니다. 응답 헤더 `X-Deleted-Kind`가 `page`인지
  `redirect`인지 알려줍니다. 오래된 이름으로 본문을 날려버리는 쪽이 둘 중 훨씬
  나쁜 실패입니다

읽기와 편집은 별칭을 따라갑니다. `GET`은 대상 문서를 돌려주면서 `redirected_from`에
요청한 이름을 담고, `PUT`·이력·diff·역링크도 모두 실제 문서로 해결됩니다. 역링크는
추가로 **그 문서의 모든 옛 이름으로 작성된 링크까지 찾습니다.** 그러지 않으면
rename 직후 자기 역링크 목록이 비어버립니다.

문서를 삭제하면 `redirect → page` 외래 키 캐스케이드로 별칭도 함께 사라지고, 그
이름들을 가리키던 링크는 다시 빨간 링크가 됩니다.

## 마크업

CommonMark에 표와 취소선을 더했습니다. 원문의 raw HTML은 비활성화돼 있어서 본문으로
script 태그를 밀어넣을 수 없습니다.

`[[대상]]`과 `[[대상|표시할 텍스트]]`로 다른 문서를 링크합니다. 대상은 제목과 같은
슬러그 변환기를 거치므로 `[[홈 페이지]]`와 "홈 페이지"라는 제목의 문서가 `홈-페이지`
슬러그에서 만납니다. 비ASCII 문자는 하이픈으로 뭉개지지 않고 그대로 남습니다.

링크는 살아있는 문서, 옛 이름, 없음 셋 중 하나로 해결됩니다. 렌더링된 `<a>`에는
`data-exists`가 붙고, 옛 이름이면 `data-redirect="true"`와 `wikilink-redirect`
클래스가 추가됩니다. 같은 구분이 각 문서의 `links` 배열에 `exists` / `via_redirect`로
나옵니다.

## 목차

헤딩(`#`~`######`)마다 제목과 같은 슬러그 변환기로 앵커를 붙입니다. 렌더링된 HTML의
`<h2 id="설치">`가 그 앵커이고, `/api/pages/{slug}/outline`이 본문·렌더링 없이 헤딩
목록만 돌려주는 이유는 그걸 얻는 데 페이지 전체를 읽을 필요가 없게 하기 위해서입니다
— 본문이 커질수록, 특히 MCP로 LLM에 넘길 때 절약되는 토큰이 커집니다.

같은 제목이 두 번 나오면 `overview`, `overview-2`처럼 번호가 붙고, 슬러그로 만들
글자가 하나도 없는 헤딩(`### !!!`)은 `section-3`처럼 문서 안 위치로 대체됩니다.

목차의 앵커 하나를 골라 `/api/pages/{slug}/sections/{anchor}`로 요청하면 그 헤딩과
그 아래 하위 헤딩까지만 렌더링해 돌려줍니다 — 다음에 나오는 같은 레벨(또는 더 얕은
레벨) 헤딩 직전에서 끊깁니다. 위키피디아의 섹션 편집과 같은 경계 규칙입니다.

## 출처

`[[위키링크]]`가 위키 안쪽을 가리킨다면, 출처는 바깥쪽을 가리킵니다. 쓰는 방법이
둘입니다.

| 문법 | 쓸 때 |
|---|---|
| `[^이름]` + 정의 줄 | 그 문서에서만 쓰는 일회성 출처 |
| `[^@키]` | [레지스트리](#출처-레지스트리)에 등록된, 여러 문서가 공유하는 출처 |

아래는 첫 번째입니다. 문장 끝에 `[^이름]`을 붙이고 어딘가에 그 이름의 정의를
적습니다.

```markdown
위키피디아는 델타 기반 시스템을 사용한다.[^mw-text]
압축은 편집과 분리된 별도 작업으로 돌린다.[^mw-text]

[^mw-text]: https://www.mediawiki.org/wiki/Manual:Text_table "MediaWiki Manual: Text table"
```

문장에는 위첨자 `[1]`만 남고, 본문 아래에 `<section class="citations">` 목록이
붙습니다. 같은 이름을 두 번 인용하면 항목은 하나이고 되돌아가는 링크가 `a` `b`로
갈라집니다. **번호는 정의 순서가 아니라 본문에서 처음 참조된 순서**입니다. 읽는
사람에게는 1, 2, 3이 페이지를 내려가는 순서여야 하니까요.

MediaWiki의 `<ref>본문</ref>`을 쓰지 않은 이유는 [마크업](#마크업)과 같습니다.
원문의 raw HTML이 꺼져 있고, URL을 문장 한가운데 박아 넣으면 편집 화면에서
문장을 읽을 수 없게 됩니다.

정의와 참조는 서로를 필요로 합니다:

| 상황 | 결과 |
|---|---|
| 정의 없는 `[^2]` | 각주가 아니라 그냥 텍스트 |
| 참조 없는 정의 | 색인도 목록도 되지 않음 |
| `http`/`https`가 아닌 URL | 정의로 인정하지 않음 |

정의 없는 참조를 살려두면 `[^2]` 같은 평범한 문장이 죽은 각주 표시로 변합니다.
참조 없는 정의를 색인하지 않는 것은 `pagelink`가 실제로 걸린 링크만 담는 것과 같은
규칙입니다. 스킴 제한은 XSS 방어선입니다 — `javascript:`는 독자가 확인하러 갈 수
있는 출처가 아닙니다.

`[^@키]`에는 이 규칙이 적용되지 않습니다. `@`가 이미 "이건 인용이다"라고 말하고
있어서 평범한 문장과 헷갈릴 일이 없고, 그래서 정의 줄도, 등록된 키일 필요도 없습니다
— `[[아직 없는 문서]]`가 그대로 링크인 것과 같습니다.

### 왜 테이블에 넣는가

`citation`은 `pagelink`의 바깥쪽 쌍둥이입니다. 수명도 같아서 편집마다 통째로
교체됩니다. 본문에만 두면 "이 URL을 어느 문서들이 쓰고 있나"를 전문 검색으로
어림잡아야 하는데, 인용은 정확히 알아야 하는 정보입니다.

```
GET /api/citations?url=https://www.mediawiki.org/wiki/Manual:Text_table
  → 이 출처를 인용한 문서 전부 (역인덱스)

GET /api/citations?host=git-scm.com
  → 도메인 하나가 통째로 죽었을 때 손봐야 할 문서 전부
```

`host`를 URL에서 따로 뽑아 저장하는 이유가 두 번째 줄입니다. 링크 썩음(link rot)은
URL 하나씩이 아니라 도메인 단위로 옵니다.

## 출처 레지스트리

인라인 정의는 **그 문서의 것**입니다. 같은 자료를 다섯 문서가 인용하면 정의도 다섯
벌이고, 제목의 오타를 고치려면 다섯 군데를 고쳐야 하고, 문서를 지우면 출처도 같이
사라집니다. 그래서 출처 자체를 문서와 별개로 관리하는 자리를 뒀습니다.

```
POST /api/sources
{ "key": "mw-text-table", "kind": "link",
  "title": "MediaWiki Manual: Text table",
  "url": "https://www.mediawiki.org/wiki/Manual:Text_table",
  "author": "MediaWiki", "published": "2024", "locator": "Storage 절" }
```

이후 모든 문서에서 **정의 줄 없이** `[^@mw-text-table]` 한 번이면 됩니다.

### 종류가 셋이다

출처가 전부 링크인 것은 아닙니다. `kind`가 그 출처가 무엇인지 정합니다.

| `kind` | 담는 것 | 필수 | 어디에 저장되나 |
|---|---|---|---|
| `link` | 웹 주소 | `url` | `source.url` |
| `text` | 인용문 자체 (책, 인터뷰, 오프라인 자료) | `text` | 불변 `text` 저장소 |
| `file` | 원본 파일 (스캔본, PDF, 사진) | 바이트는 따로 업로드 | `file` 테이블 |

`text` 종류의 인용문이 문서 본문과 **같은 저장소**로 가는 게 핵심입니다. 512바이트가
넘으면 gzip되고, 문자열은 불변이며, 수정하면 새 행이 생깁니다. 출처용 저장 코드를
따로 쓸 이유가 없었습니다.

파일은 DB 안에 바이트째로 들어가고 **sha256으로 키잉**됩니다. 같은 파일을 두 출처에
붙이면 한 번만 저장되고, 마지막으로 가리키던 출처가 사라질 때 지워집니다.

```
PUT /api/sources/scan-01/file?filename=스캔.pdf
Content-Type: application/pdf
<raw bytes>
```

multipart가 아니라 **본문이 곧 파일**입니다. JSON API에 업로드 하나 때문에 폼 파서를
들이는 건 과합니다. 크기 상한은 `max_file_bytes`(기본 10MB)이고, 선언된
`Content-Length`를 믿지 않고 스트림을 세면서 넘으면 끊습니다.

내려받기는 이미지·PDF·평문만 `inline`이고 나머지는 전부 `attachment`입니다. 업로드된
HTML이나 SVG를 같은 오리진에서 inline으로 내주면 그게 곧 스크립트 실행이라,
본문에서 raw HTML을 막아둔 것이 파일 경로로 되돌아오게 됩니다.

### 정체성과 주소, 다시

`source.id`가 정체성이고 `source.key`가 주소입니다. `page`와 같은 분리이고, 결과도
같습니다 — **출처를 고치면 인용한 모든 문서가 같이 고쳐집니다.**

```
PUT /api/sources/mw-text-table   { "title": "고친 제목" }
  → 이 출처를 인용한 문서 전부가 다음 읽기에서 새 제목을 보여줌
```

`citation` 행이 **키만 담고 제목 사본을 담지 않기** 때문입니다. 사본을 뒀다면 지금쯤
고쳐야 할 자리가 두 곳이었을 겁니다.

`kind`와 `key`는 수정할 수 없습니다. kind는 그 출처가 *무엇인지*이고, key는 문서
본문이 적어둔 이름입니다.

출처를 지우면 인용은 **끊어진 채로 남습니다** — 위키링크가 가리키던 문서를 지웠을
때와 같습니다. 본문은 여전히 `[^@key]`라고 적혀 있고, 렌더 결과가 `missing`이 될
뿐입니다. `DELETE`는 그래서 `X-Dangling-Citations` 헤더로 몇 개 문서가 그렇게 됐는지
알려줍니다.

### 세 가지 상태

위키링크가 살아있음/옛이름/없음 셋이듯, 인용도 셋입니다.

| 본문 | 렌더 | `kind` |
|---|---|---|
| `[^blog]` + 정의 줄 | 그 문서만의 일회성 출처 | `inline` |
| `[^@key]`, 등록됨 | 레지스트리 내용으로 채워짐 | `link`/`text`/`file` |
| `[^@key]`, 미등록 | `cite-missing`, `data-exists="false"` | `missing` |

세 번째가 **인용의 빨간 링크**입니다. 문서를 먼저 쓰고 출처를 나중에 등록해도 되고,
등록하는 순간 모든 문서에서 채워집니다.

### 각주에 찍히는 것

등록된 출처는 각주 목록에 서지 정보까지 나옵니다.

```html
<li id="cite-2" data-kind="text">
  <a class="cite-back" href="#cite-ref-2-0">↑</a>
  <a class="cite-source" href="/sources/kim-2004">한국어 정보검색</a>
  <span class="cite-meta">
    <span class="cite-author">김철수</span>,
    <span class="cite-published">2004</span>,
    <span class="cite-locator">112쪽</span></span>
  <a class="cite-key" href="/sources/kim-2004" data-source="kim-2004"
     data-exists="true">@kim-2004</a></li>
```

필드마다 span이 따로입니다. 클라이언트가 순서를 바꾸거나 일부만 쓸 수 있어야 하고,
쉼표는 원문 HTML을 읽는 사람을 위한 것입니다. 비어 있는 필드는 아예 나오지 않고,
셋 다 비면 `cite-meta`도 없습니다.

**인라인 정의에는 서지 정보가 없습니다.** `[^이름]: URL "제목"`에 저자와 쪽수를 적을
자리가 없고, 만들지도 않았습니다. 그런 게 필요한 자료는 레지스트리에 등록할 값어치가
있는 자료입니다.

값이 렌더에 들어간다는 건 [`cite_state`](#렌더-캐시)가 이것들까지 지켜봐야 한다는
뜻입니다. 출처의 지문에 `author|published|locator`가 함께 들어가는 이유입니다 —
저자만 고쳐도 인용한 모든 문서의 캐시가 무효화됩니다.

### 렌더 캐시

인라인 정의는 캐시를 무효화하지 않습니다. 본문만 보고 결정되니까요. **등록된
출처는 다릅니다** — 본문이 그대로여도 남이 출처를 고치거나 지울 수 있습니다.

그래서 캐시 행에 `link_state` 옆에 `cite_state`를 하나 더 둡니다. 링크가 빨강↔파랑을
오갈 때와 정확히 같은 장치이고, 감시 대상만 다릅니다.

```
link_state  = 해시( 위키링크가 어떻게 해결됐는가 )
cite_state  = 해시( 인용한 출처들이 그때 어떤 상태였는가 )
```

출처의 지문은 `updated_at`만이 아니라 렌더에 들어가는 값 전부
(`kind|title|url|author|published|locator`)를 묶습니다. 같은 밀리초 안에 두 번 고쳐도
변경으로 잡히게요.

## 검색

FTS5의 `trigram` 토크나이저를 씁니다. 부분 문자열 매칭이 되기 때문인데, 한국어에는
이게 필요합니다. `unicode61`은 공백으로 구분된 토큰 전체만 매칭해서 `위키`로
`위키시스템`을 찾지 못합니다.

다만 **trigram은 3글자 미만 쿼리를 매칭하지 못하고, 2글자 한국어 검색어는 흔합니다.**
그런 쿼리는 `LIKE '%…%'` 스캔으로 넘어갑니다. 이 폴백은 결과 첫 페이지에서 인덱스가
놓친 것도 함께 잡아줍니다. 인덱스 테이블 풀스캔이라 SQLite가 적합한 규모에서는
문제없지만, 코퍼스가 커지면 가장 먼저 손봐야 할 지점입니다.

사용자 입력은 `MATCH`에 닿기 전에 인용부호로 감쌉니다. 쿼리에 섞인 FTS5 연산자가
오류를 내거나 검색 의미를 바꾸지 않고 문자 그대로 처리됩니다.

## 시맨틱 검색

trigram은 **글자가 겹치는지**만 봅니다. "실행 취소"로 검색하면 본문에 "undo"라고만
적힌 문서는 찾지 못합니다. `/api/search/semantic`은 임베딩 벡터의 코사인 유사도로
**의미가 비슷한지**를 봐서 이 틈을 메웁니다.

### 제공자는 갈아 끼우는 부품

`omnilog/embeddings/base.py`의 `EmbeddingProvider`가 계약의 전부입니다 —
`embed_documents(texts)`와 `embed_query(text)` 두 메서드뿐입니다. 이 둘을 나눠둔
이유는 일부 모델(특히 instruction-tuned 모델)이 쿼리와 문서를 다르게 다뤄야 하기
때문입니다 — 예를 들어 쿼리에만 지시문을 붙이는 식. 그 차이는 구현체 안에 갇혀
있고, 호출하는 쪽은 몰라도 됩니다.

기본 구현은 `omnilog/embeddings/openai.py`의 OpenAI API 클라이언트입니다.
`OMNILOG_EMBEDDING_BASE_URL`을 OpenAI 호환 로컬 서버(vLLM, TEI, Ollama 등)로 돌리면
코드 변경 없이 로컬 오픈소스 모델로 옮겨갈 수 있습니다 — 단, 프리픽스 방식이 다른
모델(예: Qwen3-Embedding 계열)로 완전히 갈아탈 때는 그 모델 전용
`EmbeddingProvider` 구현체를 하나 추가하는 편이 낫습니다.

```bash
export OMNILOG_EMBEDDING_PROVIDER=openai        # 지금은 이거 하나뿐
export OMNILOG_EMBEDDING_MODEL=text-embedding-3-small
export OMNILOG_EMBEDDING_DIMENSIONS=1536
export OMNILOG_EMBEDDING_BASE_URL=              # 비우면 OpenAI 공식 엔드포인트
export OMNILOG_EMBEDDING_API_KEY=               # 비우면 OPENAI_API_KEY 사용
```

### 저장과 무효화

`page_embedding`은 `(page_id, anchor)`로 키잉됩니다. `anchor`는 지금은 항상 `''`
(페이지 전체 한 청크)지만, 나중에 섹션 단위로 쪼개도 스키마를 바꿀 필요가
없습니다. `render_cache`가 `link_state`/`cite_state`로 캐시가 무엇을 기준으로
만들어졌는지 남기는 것과 같은 이유로, 모든 행에 `model_id`·`dimensions`를 함께
찍어둡니다. 모델을 바꾸면 기존 벡터가 자동으로 "낡은" 것으로 판정되고, 검색도
현재 모델의 벡터만 골라서 봅니다 — 서로 다른 모델의 벡터를 한 결과에 섞는 일은
없습니다.

`rev_id`가 아니라 `page_id`로 키잉한 것도 의도적입니다. 이름 변경은 `page.slug`만
바꾸고 `page.id`는 그대로 두므로, rename 뒤에도 재인덱싱 없이 그대로 검색됩니다 —
[정체성과 주소는 다르다](#정체성과-주소는-다르다)와 같은 설계입니다. 편집만 새
`rev_id`를 만들어 벡터를 낡게 만듭니다.

### 편집 경로에 넣지 않은 이유

`create_page`/`update_page`는 임베딩을 계산하지 않습니다. 임베딩은 외부(지금은
OpenAI)로 나가는 HTTP 호출이고, 이 프로젝트는 [출처의 링크 생존 여부를 확인하지
않는 것](#만들지-않은-것)과 같은 이유로 편집 경로에 외부 의존성을 넣지 않습니다.
대신 `POST /api/maintenance/reindex-embeddings`를 명시적으로 호출합니다 —
`compact`처럼 오프라인 유지보수 작업입니다. 이미 최신인 페이지는 건드리지 않으므로
언제 다시 돌려도 안전하고, 페이지마다 개별 트랜잭션으로 커밋되므로 중간에 실패해도
그때까지 인덱싱된 페이지는 남습니다.

### 검색은 브루트포스

전용 벡터 인덱스 없이 저장된 벡터를 전부 훑어 코사인 유사도로 정렬합니다
(`omnilog/vectorstore.py`). trigram 인덱스가 거는 것과 같은 규모 내기입니다 —
위키가 SQLite에 편하게 들어가는 동안은 문제없고, 코퍼스가 커지면 이 모듈을
sqlite-vec이나 Qdrant 같은 전용 벡터 인덱스로 바꾸면 됩니다. 호출하는 쪽은
`(row, score)` 쌍만 다루므로 바뀌는 걸 모릅니다.

## 동시성

쓰기는 `BEGIN IMMEDIATE`로 시작합니다. 두 편집자가 동시에 read-then-upgrade로 들어가
교착하는 걸 막습니다. `PUT`에 `base_revision`을 실으면 남의 편집을 조용히 덮어쓰는
대신 `409`를 받습니다. 제목과 본문이 모두 현재 리비전과 같은 편집은 no-op이며 이력을
늘리지 않습니다.

## 만들지 않은 것

인증, 이름공간(namespace), 틀/틀 삽입(transclusion), 그리고 HTML 프론트엔드 —
API는 JSON 전용입니다. 파일은 출처로만 올릴 수 있고 문서 본문에 끼워 넣는 문법은
없습니다.

인용한 URL이 **아직 살아있는지는 확인하지 않습니다.** 바깥으로 HTTP 요청을 나가는
일이라 이 프로젝트의 "외부 의존성 없음"과 성격이 다릅니다. 필요하면 `citation`과
`source`를 도메인별로 훑는 점검 작업을 얹으면 되고, 그러라고 `host`를 뽑아뒀습니다.

**출처에는 이력이 없습니다.** 문서는 저작물이라 누가 무엇을 고쳤는지가 중요하지만,
출처는 "무엇을 가리키는가"의 기록이라 최신 답만 있으면 됩니다. 인용문(`text` 종류)의
본문만은 불변 저장소에 쌓이므로, 필요해지면 `source`에 리비전을 얹는 일이 나머지 절반
없이 가능합니다.

**출처 키는 바꿀 수 없습니다.** 문서 본문이 적어둔 이름이라, 바꾸면 인용이 조용히
끊어집니다. 문서 rename은 별칭(`redirect`)이 받아주지만 출처에는 그 장치가 없습니다.
필요해지면 같은 모양의 별칭 테이블을 하나 더 두면 됩니다.

이름을 바꿔도 **본문 안의 `[[링크]]` 원문은 고쳐지지 않습니다.** 별칭이 받아주므로
동작에는 문제가 없고 MediaWiki도 같은 방식이지만, 원문까지 실제로 갱신하는 링크
수리가 필요하면 `pagelink` 역인덱스로 대상 문서를 찾아 일괄 편집하는 작업을 얹으면
됩니다.
