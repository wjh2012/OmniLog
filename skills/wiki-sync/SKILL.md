# OmniLog 위키 동기화

이 스킬은 이 저장소(OmniLog) 자체가 제공하는 위키를, 이 저장소를 개발하면서
"제품이 자기 자신을 문서화"하는 데 씁니다. REST API가 아니라 `omnilog` MCP
서버(도구 목록에 `omnilog__*` 형태로 노출됩니다)를 통해서만 호출하세요.

## 언제 쓰나

- 새 기능(엔드포인트, 동작, 정책 변경 등)을 구현했을 때
- 기존 기능의 동작을 바꿨을 때 (버그 수정으로 인한 동작 변화 포함)
- `hooks/hooks.json`의 알림 훅이 "위키 갱신을 확인하라"는 리마인더를 띄웠을 때

리팩터링처럼 외부에서 관찰 가능한 동작이 전혀 바뀌지 않는 변경에는 쓰지 않습니다.

## 절차

1. **변경 파악**: `git diff` / `git log -1 --stat` 등으로 이번 작업에서 실제로
   바뀐 내용을 요약합니다. 무엇을, 왜 바꿨는지 한두 문장으로 정리하세요.

2. **대상 문서 찾기**: 변경된 기능/모듈을 대표하는 제목을 정하고, `omnilog`
   MCP의 검색 도구(`GET /api/search`에 대응)로 이미 문서가 있는지 확인합니다.
   슬러그·용어는 `GLOSSARY.md`와 기존 위키 문서의 표기를 따르세요.

3. **등록 또는 갱신**:
   - 문서가 없으면 문서 생성 도구(`POST /api/pages`에 대응)로 새로 만듭니다.
     본문은 CommonMark로 작성하고, 관련 문서가 있으면 `[[문서 제목]]` 위키링크로
     연결합니다.
   - 문서가 있으면 먼저 현재 리비전을 조회(`GET /api/pages/{slug}`)해
     `latest_revision` 번호를 확인한 뒤, 새 리비전 저장 도구(`PUT
     /api/pages/{slug}`에 대응)를 그 `base_revision`과 함께 호출해 편집
     충돌(409)을 피합니다. 편집 요약(edit summary)에는 무엇이 왜 바뀌었는지
     적습니다.

4. **내용 기준**: 실제 diff에 있는 내용만 반영하세요. 코드에 없는 동작을
   지어내지 마세요. 필요하면 영향받는 엔드포인트/파일 경로, 날짜를 함께
   적습니다.

5. **결과 보고**: 사용자에게 생성/갱신한 문서의 제목, 슬러그, 리비전 번호를
   한 줄로 알려주세요.

## CLAUDE.md의 Artifact 갱신 규칙과의 관계

`CLAUDE.md`는 기능 변경 시 외부 Claude 아티팩트(URL로 지정된 위키)도 갱신하라고
요구합니다. 이 스킬은 그것과 별개로 **OmniLog가 직접 서빙하는 자체 위키**를
갱신하는 절차입니다. 두 가지는 서로 대체하지 않으므로, 기능 변경 후에는 둘 다
확인하세요.

## 사전 조건

`omnilog` MCP 서버가 붙으려면 OmniLog 앱이 실행 중이어야 합니다:

```bash
uv run uvicorn main:app --reload
```

기본 접속 주소는 `http://127.0.0.1:8000/mcp`이며, 다른 주소를 쓰려면
`OMNILOG_MCP_URL` 환경변수를 설정하세요. `OMNILOG_API_KEYS`로 인증을 켠
환경이라면 `mcp/omnilog.mcp.json`에 `editor` 역할 토큰을 담은 `Authorization`
헤더를 추가해야 쓰기 도구를 호출할 수 있습니다.
